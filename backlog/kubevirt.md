# KubeVirt

Assessment of running VMs on this cluster and of contributing OpenShift Virtualization to okderators; not built. The README TODO keeps a short summary of the item and links here.

**KubeVirt — ASSESSED 2026-09-14: install the community HCO if VMs are wanted; do NOT port OpenShift Virtualization to okderators.** The ask was whether to bring the OpenShift Virtualization operator into `okd-operator-pipeline`. Findings: (1) **it is already reachable** — `community-kubevirt-hyperconverged` sits in `community-operators` (`stable` = `kubevirt-hyperconverged-operator.v1.17.3`, built 2026-06-28, KubeVirt v1.7.4, `AllNamespaces` only) and in `operatorhubio-catalog` (v1.18.1), and the bundle already ships the OpenShift console plugin (`kubevirt-plugin` v4.20.15) plus CDI, CNAO, SSP, HPP, AAQ and WASP — the same components the Red Hat product is built from, all public in the `kubevirt` org; (2) **okderators has never carried it** — zero issues or PRs mentioning kubevirt in `okd-operator-pipeline`, and a port would mean a dozen submodules and ~30 images for a SCOS rebuild of what (1) already provides, against the cert-manager PRs' three submodules that are still unmerged; (3) **this cluster can host VMs**: 128 GiB RAM per node with memory requests at 12/28/34%, i7-11700 VT-x, `ceph-nvme-block` (layering only, expansion on, `ceph-rbd-snapshot` present) gives CDI clones and RBD `Block`+`RWX` for live migration, at ~310 GiB pool MAX AVAIL, i.e. a handful of VMs, not a fleet; (4) **costs to plan for**: every VM with `evictionStrategy: LiveMigrate` adds a `minAvailable: 1` PDB and a migration to every drain — on top of the immich-postgres blocker, on a cluster that rerolled by accident today; LAN-bridged VM networking is an NNCP enactment (candidate NIC: the unused `enp1s0f1np1`), i.e. the `br-ex.forwarding` pre-flight; CPU requests already read 88%/86% on node5/node6, so pods-network-only VMs first.

**Shape when wanted (bounded, approval first):** `components/operators/kubevirt/` = Namespace `kubevirt-hyperconverged` + OperatorGroup `spec: {}` + Subscription (`community-operators`, `stable`) at wave 1, `HyperConverged/kubevirt-hyperconverged` at wave 5; gate with one DataVolume on RBD and one live migration before any real VM.

**Contribution frame, re-assessed the same day (okderators exists to rebuild Red Hat's operators for OKD, ODF being the model):** the ODF entry is 20 submodules of public `red-hat-storage/*` midstream forks on `release-4.21`, 22 Containerfiles on UBI/CentOS bases, a 20 KB `build.sh` and a `patches/` dir. OpenShift Virtualization has **no public midstream**: the product CSV (`kubevirt-hyperconverged-operator.v4.21.x`) is generated inside Red Hat's build from `kubevirt/hyperconverged-cluster-operator`, whose `deploy/olm-catalog` holds only the community package — so a port rebuilds upstream `kubevirt`-org tags, not Red Hat's tree. The pin list is in HCO `release-1.17` `hack/config` (KubeVirt v1.7.4, CDI v1.64.0, CNAO v0.101.2, SSP v0.24.1, TTO v0.5.0, HPP v0.24.0, AAQ v1.6.0, WASP v1.2.2, migration operator v0.0.14, console plugin v4.20.15-rc.0, console proxy v0.0.12, four CSI sidecars) — about 12 repos and 30 images, 1.5× ODF. HCO's own `hack/build-manifests.sh` already parametrises every image, the package name and the namespace (`OPERATOR_NAMESPACE`), so the bundle step is ODF-shaped; what has no ODF analogue is `virt-launcher`/`virt-handler`, which carry libvirt+qemu via KubeVirt's RPM lockfiles against CentOS Stream 9 and would need re-resolving on a SCOS/c10s base, plus libguestfs and virtio-win images. Demand signal is weak: the OKD operator wishlist (okd-project/okd#456) listed KubeVirt under "available in the community catalog" while descheduler sat under "unavailable" and was later added, and `okd-operator-pipeline` has zero issues or PRs mentioning kubevirt. Merge risk is real: the three-submodule cert-manager PRs (#28/#29) are still open, and the 4.21 index just shipped a 4.22-built descheduler.

**Recommended path:** (1) open an issue/discussion proposing `virtualization/` (HCO-driven, upstream pins, SCOS Containerfiles, `OPERATOR_NAMESPACE=openshift-cnv`) and get a maintainer yes/no before building anything; (2) if yes, phase 1 = HCO + KubeVirt core + CDI (~20 images, a bootable VM), phase 2 = CNAO/SSP/HPP/AAQ/plugin, e2e on this cluster (KVM-capable, RBD RWX-Block) via `operator-sdk run bundle` — user-run, it installs CRDs cluster-wide; (3) an x86_64 build host is required, the Mac is arm64 and KubeVirt builds are Go+RPM heavy. Cheaper first contribution to the same repo with direct payoff here: fix the descheduler 4.21 build (item under *Queued — operators / catalog*).

**CLOSED 2026-09-14: not worth it.** The OKD documentation's own install procedure (`virt/install/installing-virt.html`) IS the community HCO — `openshift-docs` `enterprise-4.21` `_attributes/common-attributes.adoc` sets, under `ifdef::openshift-origin[]`, `VirtProductName: OKD Virtualization`, `CNVOperatorDisplayName: KubeVirt HyperConverged Cluster Operator`, `CNVSubscriptionSpecSource: community-operators`, `CNVSubscriptionSpecName: community-kubevirt-hyperconverged`, `CNVNamespace: kubevirt-hyperconverged`. "OKD Virtualization" is by definition the package already in our catalog; an okderators rebuild would duplicate the documented product with no consumer. Only the "install it here if VMs are wanted" half of this item remains live.
