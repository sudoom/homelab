# `csi-rbd-provisioner.<gen>` user created with missing `osd profile rbd` cap on fresh bootstrap

**Upstream:** https://github.com/rook/rook
**Component:** `pkg/operator/ceph/client/` (CSI keyring provisioning)
**Affected version:** Rook v1.19.5 (latest at time of writing) on Ceph Squid 19.2.3 (deployed via OKD 4.20 / Kube 1.31)
**Severity:** Functional — every RBD `CreateVolume` hangs on a freshly-bootstrapped cluster until the cap is manually added. CSI is the only block-storage path on the cluster; every new PVC stays `Pending` indefinitely.

## Summary

On a fresh `CephCluster` bootstrap with `network.provider: host` + `addressRanges`, the Ceph user generated by Rook for the CSI RBD provisioner (`client.csi-rbd-provisioner.1`) ends up with incomplete capabilities — the `osd` cap is missing entirely:

```
client.csi-rbd-provisioner.1
  caps mgr "allow rw"
  caps mon "profile rbd, allow command 'osd blocklist'"
  (no osd cap)
```

Compare with the three other CSI users that Rook provisions in the same reconcile cycle on the same cluster, which all received correct caps:

| User | mon cap | osd cap |
|---|---|---|
| `client.csi-rbd-node.1` | `profile rbd` | `profile rbd` ✓ |
| `client.csi-rbd-provisioner.1` | `profile rbd, allow command 'osd blocklist'` | **missing** ✗ |
| `client.csi-cephfs-node.1` | (via mds path) | `allow rwx tag cephfs metadata=*, allow rw tag cephfs data=*` ✓ |
| `client.csi-cephfs-provisioner.1` | (via mds path) | `allow rw tag cephfs metadata=*` ✓ |

Only the RBD-provisioner path is affected. The `mon` cap correctly carries the provisioner-specific `allow command 'osd blocklist'` (needed for fencing on attach-failover), so the template clearly knows this user is a provisioner — it just doesn't include the `osd profile rbd` cap.

Without the `osd` cap, the CSI driver can authenticate to mons but cannot perform any RADOS-level write. Every `CreateVolume` RPC silently hangs until the gRPC deadline (~2 min), at which point it returns `DeadlineExceeded → RST_STREAM CANCEL`. The retry hits the rbd-plugin's in-memory operation tracker (which still holds the lock from the cancelled call) and returns `Aborted: an operation with the given Volume ID ... already exists` forever after. Symptom looks like the well-known "operation already exists" mount lock from rbd-plugin in-memory tracker, but the underlying cause is one layer further down — Ceph is rejecting the auth, not the plugin tracker itself.

## Steps to reproduce

1. Tear down a Rook-managed `CephCluster` (e.g. via `cleanupPolicy.confirmation: "yes-really-destroy-data"` + chart disable + the documented full cleanup sweep).
2. Re-bootstrap the `CephCluster` on the same namespace with the rook-ceph operator running (operator NOT torn down).
3. Once `HEALTH_OK`, apply a `PersistentVolumeClaim` against the RBD `StorageClass`:
   ```yaml
   apiVersion: v1
   kind: PersistentVolumeClaim
   metadata:
     name: csi-bug-repro
     namespace: default
   spec:
     accessModes: [ReadWriteOnce]
     storageClassName: ceph-nvme-block
     resources:
       requests:
         storage: 1Gi
   ```
4. Watch the PVC stay `Pending`. The csi-provisioner sidecar's `csi-rbdplugin` log will show:
   ```
   E0515 ... ID: N Req-ID: pvc-... an operation with the given Volume ID pvc-... already exists
   E0515 ... GRPC error: rpc error: code = Aborted desc = an operation with the given Volume ID ... already exists
   ```
   …after an initial `code = DeadlineExceeded desc = stream terminated by RST_STREAM with error code: CANCEL`.

## Expected behavior

`client.csi-rbd-provisioner.1` should be provisioned with the canonical caps shape that the rbd-node user already gets:

```
caps mgr "allow rw"
caps mon "profile rbd, allow command 'osd blocklist'"
caps osd "profile rbd"
```

This is the standard caps template for the RBD CSI provisioner across upstream Ceph + Rook documentation (e.g. <https://github.com/ceph/ceph-csi/blob/devel/docs/capabilities.md>).

## Actual behavior

The `osd profile rbd` cap is missing. The user can authenticate to mons but cannot perform pool I/O.

The operator log shows two `getOrCreate` calls for the same user during bootstrap (the second from a later reconcile pass), but the second call does NOT update caps once the user already exists:

```
2026-05-15 08:02:03.794635 I | cephclient: getting or creating ceph auth key "client.csi-rbd-provisioner.1"
2026-05-15 08:02:56.634135 I | cephclient: getting or creating ceph auth key "client.csi-rbd-provisioner.1"
```

Both calls succeed and produce the same (incomplete) caps shape.

## Workaround

Run these three steps in order before applying any PVC against the RBD StorageClass:

**1. Fix the caps:**
```
oc -n rook-ceph exec deploy/rook-ceph-tools -- \
  ceph auth caps client.csi-rbd-provisioner.1 \
    mgr "allow rw" \
    mon "profile rbd, allow command 'osd blocklist'" \
    osd "profile rbd"
```

**2. Clear any orphan CSI omap state.** If a PVC was already attempted while the cap was missing, the failed `CreateVolume` left a half-written entry in `csi.volumes.default` *plus* a per-volume metadata object — the in-memory plugin tracker stays locked on that volume ID even after a plugin restart because the omap entry "proves" an in-flight operation exists. Inspect and clear:
```
oc -n rook-ceph exec deploy/rook-ceph-tools -- rados -p <pool> listomapkeys csi.volumes.default
# for each csi.volume.pvc-<uuid> key:
oc -n rook-ceph exec deploy/rook-ceph-tools -- rados -p <pool> getomapval csi.volumes.default csi.volume.pvc-<uuid>
# note the 36-byte UUID value — that's the orphan per-volume metadata object name
oc -n rook-ceph exec deploy/rook-ceph-tools -- rados -p <pool> rmomapkey csi.volumes.default csi.volume.pvc-<uuid>
oc -n rook-ceph exec deploy/rook-ceph-tools -- rados -p <pool> rm csi.volume.<orphan-uuid>
```

**3. Restart the rbd-csi ctrlplugin pods to clear the in-memory operation tracker:**
```
oc -n rook-ceph delete pod -l app=rook-ceph.rbd.csi.ceph.com-ctrlplugin
```

After Rook recreates the pods and re-acquires the leader lease, the queued PVC is provisioned within seconds.

If the bug ever rotates keys to `csi-rbd-provisioner.2`/`.3`/…, the same `ceph auth caps` command needs to be re-run against the new generation suffix. (Until the upstream fix lands, treat fresh bootstraps and rotation events as needing the workaround.)

## Notes

- The `.1` suffix on every CSI user (`csi-rbd-node.1`, `csi-cephfs-node.1`, `csi-cephfs-provisioner.1`, `csi-rbd-provisioner.1`) is the Rook key-rotation generation marker, not a leftover from prior cluster state. A fresh Ceph auth DB (new FSID) starts at `.1`.
- Confirmed not a CSI config-mismatch issue: `ceph-csi-config` ConfigMap correctly references `clusterID: "rook-ceph"`, monitors match the live `ceph mon dump`, and the StorageClass parameters reference the right `provisioner-secret-name`.
- Symptom is easily misdiagnosed as the "operation already exists" rbd-plugin in-memory tracker lock (the obvious surface error), because that lock IS present — but it is downstream of the missing osd cap. Restarting CSI plugins clears the tracker but every retry hangs again on Ceph auth.
- `ceph auth get client.csi-rbd-node.1` on the same cluster shows the correct three caps, including `osd profile rbd`. The bug is specific to the *provisioner* user template.

## Local context where this was observed

- 3-node OKD 4.20 bare-metal cluster, 3× Samsung PM9A1 NVMe (one OSD per node).
- Rook operator running through the entire teardown + re-bootstrap cycle (operator was NOT removed during teardown).
- Ceph image: `quay.io/ceph/ceph:v19.2.3`.
- `network.provider: host` with `addressRanges.public/cluster: ["192.168.10.0/24"]` (10G backnet binding for OSDs).
- Full chronology in the cluster's blog draft `blog/blog-multus-ceph-migration-draft.md` under the 2026-05-15 re-bootstrap section.
